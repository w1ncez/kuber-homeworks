### Задание. Необходимо определить требуемые ресурсы
Известно, что проекту нужны база данных, система кеширования, а само приложение состоит из бекенда и фронтенда. Опишите, какие ресурсы нужны, если известно:

1. Необходимо упаковать приложение в чарт для деплоя в разные окружения. 
2. База данных должна быть отказоустойчивой. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
3. Кеш должен быть отказоустойчивый. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
4. Фронтенд обрабатывает внешние запросы быстро, отдавая статику. Потребляет не более 50 МБ ОЗУ на каждый экземпляр, 0.2 ядра. 5 копий. 
5. Бекенд потребляет 600 МБ ОЗУ и по 1 ядру на копию. 10 копий.

----

### Правила приёма работы

1. Домашняя работа оформляется в своем Git-репозитории в файле README.md. Выполненное домашнее задание пришлите ссылкой на .md-файл в вашем репозитории.
2. Сначала сделайте расчет всех необходимых ресурсов.
3. Затем прикиньте количество рабочих нод, которые справятся с такой нагрузкой.
4. Добавьте к полученным цифрам запас, который учитывает выход из строя как минимум одной ноды. 
5. Добавьте служебные ресурсы к нодам. Помните, что для разных типов нод требовния к ресурсам разные. 
6. В результате должно быть указано количество нод и их параметры.

----

### Решение 

##### Принятые допущения:
- Все указанные потребности - ресурсы одного экземпляра приложения
- База данных и кеш должны иметь по 3 реплики
- Для отказоустойчивости предполагаем, что после потери одной ноды оставшиеся ноды смогут разместить все необходимые реплики
- Для Stateful-компонентов нужны постоянные тома, а не emptyDir
- Ресурсы Kubernetes, системных демонов и операционная система учитываются отдельно от полезной нагрузки

#### С учетом отказа одной рабочей ноды 

Для простого расчета используем схему, когда одна нода может выйти из строя, а остальные должны принять её нагрузку.<br>
Предположим, что мы выделяем под приложение 4 рабочие ноды, тогда после отказа одной останутся 3. <br>
Требуемые ресурсы на одну оставшуюся ноду в среднем:<br>
*CPU = 17/3​ ≈ 5.67* <br>
*RAM = 30.25/3 ​≈ 10.08 GB* <br>

Это средняя нагрузка, но планировать ровно под неё нельзя, нужны дополнительные ресурсы для системных процессов и пиковых нагрузок. <br>

#### Учитываем управляющие ноды Kubernetes

Если проект предполагает отказоустойчивый Kubernetes-кластер, управляющую плоскость тоже нужно учитывать.

<img width="1034" height="91" alt="image" src="https://github.com/user-attachments/assets/b8972da7-ce49-437a-a28f-10467a293aff" /> <br>

Три управляющие ноды позволяют построить отказоустойчивую control plane при корректной настройке кворума и размещении в независимых доменах отказа.<br>

В этом варианте:
- Control Plane отвечает за API Server, Scheduler, Controller Manager и etcd
- Worker-ноды выполняют пользовательские приложения
- Ресурсы Control Plane не включены в доступную емкость приложения
<br>

#### Итого инфраструктура:
- 3 Control Plane по 4 vCPU / 8 GB
- 4 Worker по 8 vCPU / 16 GB
- 7 нод
- 44 vCPU физически выделенных виртуальным машинам
- 88 GB RAM

Это проектная оценка для заданной нагрузки, а не универсальная норма для Kubernetes.
<br>

Хотелось бы также отметить, что три реплики сами по себе не гарантируют отказоустойчивость.

Есть нюансы, которые необходимо также предусмотреть.<br>
Для БД:
- StatefulSet или специализированный оператор
- репликацию данных
- механизм выбора Primary/Leader
- постоянные тома
- резервное копирование
- распределение реплик по разным Worker-нодам <br>
Для кеша необходимо определение механизма репликации и переключения при отказе узла в зависимости от выбранной архитектуры.
